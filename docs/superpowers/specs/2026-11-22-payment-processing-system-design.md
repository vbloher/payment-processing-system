# Payment Processing System — дизайн

Дата: 2026-11-22. Статус: ждёт одобрения.

Пометки в тексте: **[решил пользователь]** — сказано пользователем прямо; **[предложение]** — решение
Claude, пользователь может его поменять при ревью.

## 1. Зачем

Пет-проект для подготовки к senior-собеседованию в финтех. Небольшая, но честная система обработки
платежей на Go, в которой каждый паттерн из списка выполняет свою работу и эту работу можно показать
тестом и объяснить у доски. Ценность проекта — в защищаемых решениях и разобранных сценариях отказа,
а не в количестве фич.

## 2. Цели, не-цели, анти-цели

**Цели**

- Один денежный поток, сделанный глубоко: исходящий платёж со счёта клиента через банк, со всеми
  ветками отказа.
- Каждая технология из списка занята своим делом: PostgreSQL (платежи и леджер), outbox и inbox,
  NATS JetStream, Temporal-сага, mock-банк, сверка.
- Для каждого паттерна есть тест, который показывает отказ, от которого паттерн защищает.
- Монорепо из нескольких сервисов, каждый построен по `go-clean-architecture-template`.
- Юнит- и интеграционные тесты обязательны.
- Система поднимается локально одной командой и проходится руками по README.

**Не-цели**

- Возвраты, чарджбэки, pay-in с карты, комиссии, конвертация валют (одна валюта на платёж).
- Асинхронные вебхуки от банка.
- Аутентификация, авторизация, PCI, KYC/AML, rate limiting.
- Kubernetes, продовый деплой, кластерные NATS и Temporal.
- Redis (в шаблоне он есть; здесь не нужен, см. 6.1).
- UI, дашборды, алертинг.
- Версионирование воркфлоу Temporal.

**Анти-цели** — что сделает проект провальным, даже если он работает

- Temporal и NATS делают одну и ту же работу: событие двигает шаг платежа или Temporal рассылает
  уведомления.
- Деньги можно потерять или задвоить: неидемпотентный шаг, компенсация при неизвестном исходе.
- Паттерн стоит «для галочки»: нет сценария отказа, который он закрывает.
- Разрастание: лишние сервисы и фичи. Пользователь просил небольшую систему.

## 4. Подходы

Рассматривались три раскладки по сервисам.

**A. Четыре сервиса, леджер отдельно, сверка внутри `payment`.** Сага идёт через два участника:
`ledger` по gRPC и `mockbank` по HTTP. Сверка — Temporal Schedule в `payment`. Небольшой объём, и у
каждого пункта из списка пользователя своя работа.

**B. То же, но сверка — пятый сервис со своей БД.** Чище по владению данными. Цена: ещё один сервис
шаблонного кода и list-API в `payment` и `ledger`, нужные только сверке.

**C. Платежи и леджер в одном сервисе и одной БД.** Статус платежа и проводки меняются в одной
транзакции: самая сильная консистентность и меньше всего кода. Цена: сага вырождается до одного
внешнего участника, а пользователь просил несколько микросервисов.

**Выбран A. [предложение]** Пользователь передал проработку Claude («можно так придумать») и
подтверждает выбор при ревью этого документа. Аргумент за C («не распределяй то, что должно быть
консистентным») остаётся в README как осознанный компромисс.

## 5. Архитектура

```
client ─HTTP─▶ payment ══ Temporal saga ══▶ ledger   (gRPC: hold / capture / release)
                  │                    ╚══▶ mockbank (HTTP: transfer / cancel / statement)
                  │ outbox (та же транзакция, что и смена статуса)
                  ▼
           NATS JetStream ──▶ notification (inbox) ──▶ webhook / лог
```

Правило разделения ролей:

| Технология | Работа | Чего не делает |
|---|---|---|
| Temporal | Команды, от которых зависит исход платежа: шаги саги, ретраи, компенсация, ожидание сверки. Расписание сверки. | Не рассылает уведомления. |
| NATS JetStream | Факты после коммита для потребителей, которых платёж не ждёт. | Не запускает и не двигает шаги платежа. |
| Outbox | Атомарность «статус изменился + событие записано» в `payment`. | |
| Inbox | Эффект ровно один раз в `notification` при at-least-once доставке. | |
| Сверка | Последняя линия: находит расхождения между платежами, леджером и банком и разрешает зависшие платежи. | |

Проверочный вопрос для любой новой связи: «если получатель упал, платёж должен измениться?» Да —
это шаг Temporal. Нет — это событие в NATS.

### Сервисы

| Сервис | Что делает | Вход | Хранилище |
|---|---|---|---|
| `payment` | API платежей, сага, outbox, сверка | HTTP; воркер Temporal; воркер outbox | БД `payment` |
| `ledger` | Двойная запись, холды, балансы | gRPC | БД `ledger` |
| `notification` | Потребляет события, доставляет уведомления | consumer JetStream | БД `notification` |
| `mockbank` | Имитирует банк с управляемыми отказами | HTTP | память процесса |

Database-per-service: три базы в одном инстансе Postgres. Сервисы не читают чужие базы.

## 6. Платёж и сага

**[предложение]** Поток — исходящий платёж: клиент держит баланс в нашем леджере и переводит деньги
внешнему получателю через банк-партнёр. Этот поток выбран потому, что леджер в нём настоящий
участник саги с настоящей компенсацией.

### 6.1 API `payment`

- `POST /api/v1/payments`, заголовок `Idempotency-Key` обязателен. Тело: `account_id` (uuid),
  `amount` (int64, минорные единицы, > 0), `currency` (ISO-4217), `beneficiary` (строка),
  `description` (необязательно). Ответ `202` с `id` и текущим статусом.
- `GET /api/v1/payments/{id}` — платёж со статусом, причиной отказа, ссылкой на банковский перевод.
- `GET /api/v1/reconciliation/discrepancies` — найденные расхождения (для демо и e2e-проверок).

Идемпотентность API **[предложение]**: уникальный индекс по `idempotency_key` в Postgres плюс хэш
тела запроса. Повтор с тем же ключом и телом возвращает тот же платёж. Тот же ключ с другим телом —
`409`. Redis из шаблона не используется: его `SET NX` «открывается» при недоступности Redis и не
атомарен с записью в БД, для денег это неприемлемо.

Запуск воркфлоу **[предложение]**: сначала вставка платежа (`created`), потом `StartWorkflow` с
ID `payment-<id>`. Старт идемпотентен по ID воркфлоу. Если старт не удался, платёж остаётся в
`created`; его поднимает повтор запроса с тем же ключом или сверка (см. 8).

### 6.2 Статусы

| Из | В | Когда |
|---|---|---|
| `created` | `processing` | воркфлоу стартовал |
| `processing` | `succeeded` | capture выполнен |
| `processing` | `failed` | леджер отклонил холд (недостаточно средств, нет счёта, другая валюта); отказ банка; банк отменил перевод |
| `processing` | `review` | исход в банке неизвестен |
| `review` | `succeeded` / `failed` | сигнал от сверки |

Переход в текущий статус — no-op без второго события (ретрай активности). Любой другой переход —
неретраебельная ошибка. Машина состояний живёт в `domain` и покрыта табличными тестами.

### 6.3 Воркфлоу `PaymentWorkflow`

```
1. StartProcessing     created → processing
2. ledger.Hold         ── insufficient_funds ──────────────────▶ Fail
3. bank.Transfer       ── declined ──▶ ledger.Release ─────────▶ Fail      (компенсация)
      │ succeeded                          ▲
      │                                    │ declined / cancelled
      ├─ unknown ─▶ bank.Cancel ───────────┤        (succeeded → шаг 4)
      │                │ всё ещё unknown
      │                ▼
      │           MarkReview ─▶ ждать сигнал сверки ─▶ succeeded | failed
      ▼
4. ledger.Capture      ретраи без лимита: точка невозврата пройдена
5. Complete            → succeeded + outbox(payment.succeeded)

Fail                   → failed + outbox(payment.failed), с причиной
MarkReview             → review + outbox(payment.review_required)
```

Правила:

- **Шаги трёх видов.** `Hold` — компенсируемый. `bank.Transfer` — точка невозврата (pivot). `Capture`
  и `Complete` — только вперёд, ретраи без лимита.
- **Компенсация только при определённом отказе.** `Release` выполняется, если банк ответил `declined`
  или `cancelled`. Отсутствие перевода в банке отказом не считается: запрос, у которого на нашей
  стороне истёк таймаут, может быть ещё в пути. При неизвестном исходе холд остаётся, платёж уходит
  в `review`.
- **Неизвестный исход разрешает `bank.Cancel` [предложение].** Это идемпотентная операция банка,
  которая возвращает окончательное состояние перевода: `succeeded` или `declined`, если банк запрос
  уже обработал, иначе `cancelled`. После `cancelled` банк закрывает ссылку: запоздавший запрос на
  перевод с тем же ключом денег не двигает и возвращает `cancelled`. Без такой гарантии со стороны
  банка безопасны только ожидание и ручной разбор — это идёт в README как компромисс.
- **Каждый шаг идемпотентен.** Ключ операции в леджере и в банке — `payment_id`.
- **Ретраи.** Вызовы банка (`Transfer`, `Cancel`) — ограниченное число попыток с backoff. Вызовы
  своих сервисов (леджер, смена статуса платежа) — без лимита: до точки невозврата ничего
  необратимого не произошло, после неё останавливаться нельзя. `Release` поэтому вызывается только
  после успешного `Hold`. Долгий простой леджера сверка видит как `stuck`. Бизнес-ошибки
  (`insufficient_funds`, `declined`, ошибка валидации) неретраебельны. Числа — в конфиге, чтобы тесты
  шли быстро.
- **Сигнал** `bank-outcome` отправляет сверка. Он несёт окончательное состояние перевода в банке
  (`succeeded` | `declined` | `cancelled`), чтобы причина отказа не терялась.

## 7. Сервисы подробнее

### 7.1 `ledger`

Двойная запись **[предложение]**:

- Счёт клиента — пассив, нормальная сторона кредит. Системный счёт `bank_cash` (деньги в
  банке-партнёре) — актив, нормальная сторона дебет.
- Пополнение: Дт `bank_cash`, Кт счёт клиента. Исходящий платёж (capture): Дт счёт клиента,
  Кт `bank_cash`.
- Суммы — `int64` в минорных единицах плюс валюта. Счёт одновалютный, транзакция одновалютная,
  `bank_cash` — по одному на валюту. Проводки неизменяемы.
- Инвариант транзакции: сумма дебетов равна сумме кредитов. Проверяется в `domain` (табличные тесты).
- Целостность леджера — баланс счёта равен сумме его проводок, по каждой валюте дебетовые остатки
  равны кредитовым — проверяется в тестах после сценариев с конкуренцией. Это не RPC и не шаг сверки.
- Холд — резерв вне проводок: `available = balance − held`. Проводки появляются только при capture.
- Конкурентность: `SELECT … FOR UPDATE` по счетам в детерминированном порядке. Доступный остаток
  клиента не может стать отрицательным.

gRPC-операции: `OpenAccount`, `Deposit` (идемпотентен по ключу), `GetBalance`, `Hold`, `Capture`,
`Release`, пакетное чтение холдов по `payment_id` (для сверки). Ошибки домена отображаются в коды
gRPC; адаптер в `payment` переводит их обратно в доменные ошибки.

### 7.2 `mockbank`

HTTP-операции: создать перевод (идемпотентен по `Idempotency-Key`), отменить перевод по ссылке
клиента (контракт — в 6.3), найти перевод по ссылке клиента, выписка за период. Состояние в памяти
**[предложение]**: это мок, перезапуск его сбрасывает.

Управляемые отказы, детерминированные, по образцу тестовых карт Stripe **[предложение]** — поведение
задаёт значение `beneficiary`:

- отказ банка (`declined`);
- временная ошибка первые N попыток, потом успех;
- таймаут после обработки: деньги ушли, ответа нет;
- банк недоступен.

Плюс admin-эндпоинты: включить и выключить недоступность банка, добавить «чужой» перевод, изменить
сумму существующего — чтобы тесты и демо могли увести платёж в `review` и создать расхождение для
сверки.

### 7.3 `notification`

Потребляет события из JetStream. Обработка одного сообщения:

1. В одной транзакции: вставка в `inbox` по `event_id` (при конфликте — дубликат) и запись
   уведомления.
2. Доставка через порт `Sender`: POST на настроенный webhook с `Idempotency-Key: <event_id>`; если
   URL не задан — только лог **[предложение]**.
3. Отметка «доставлено», затем ack.

Эффект в БД — ровно один раз. Внешний вызов — at-least-once с ключом идемпотентности: при повторной
доставке уже записанное, но не доставленное уведомление доставляется снова. После исчерпания попыток
сообщение уходит в DLQ и не блокирует поток.

## 8. События и сверка

### События

Публикует `payment` через outbox: `payment.succeeded`, `payment.failed`, `payment.review_required`,
`reconciliation.discrepancy_found`.

- Outbox — по образцу шаблона: чтение с удалением и публикация в одной транзакции, at-least-once.
- У события есть свой `event_id`; он уходит в JetStream как `Nats-Msg-Id` (дедупликация на брокере)
  и служит ключом inbox.
- Формат — JSON-конверт: `id`, `type`, `occurred_at`, `payment_id`, `data`. Go-структуры событий
  лежат в общем пакете **[предложение]**: это контракт между сервисами, а не общий домен.
- Trace context идёт через outbox и заголовки NATS, как в шаблоне через Kafka.

### Сверка

`ReconciliationWorkflow` запускается Temporal Schedule в `payment`, перекрытие запусков запрещено.
**[предложение]** Schedule вместо тикера, как у outbox-воркера: при нескольких репликах он даёт
единственный запуск без распределённой блокировки.

Сверка сопоставляет три источника: платежи, переводы банка, холды леджера. Окно по времени только
отбирает кандидатов: платежи, изменённые за окно; платежи, на которые ссылается выписка банка за
окно; платежи с открытыми расхождениями. Вывод по каждому кандидату делается по точечным запросам
в банк и леджер, а не по попаданию записи в окно, — иначе граница окна рождает ложные расхождения.
Перевод из выписки без платежа — `bank_unexpected`. Платёж не в конечном статусе даёт только `stuck`.
Сравнение по одному платежу — чистая функция в `domain` с табличными тестами.

| Расхождение | Смысл |
|---|---|
| `bank_missing` | платёж `succeeded`, в банке перевода нет |
| `bank_unexpected` | в банке успешный перевод, а платёж `failed` или его нет |
| `amount_mismatch` | сумма или валюта не совпадают |
| `ledger_mismatch` | состояние холда не соответствует статусу платежа |
| `stuck` | платёж не в конечном статусе дольше порога |

Расхождение записывается один раз, сколько бы запусков его ни увидело, и уходит событием в NATS.
Запуск, который открытое расхождение больше не воспроизводит, закрывает его. Ручной разбор
расхождений — вне проекта.

Сверка сама исправляет только два случая **[предложение]**:

- платёж в `review`: вызывает `bank.Cancel` и, получив окончательное состояние, шлёт сигнал
  воркфлоу. Отсутствие перевода в выписке исходом не считается;
- платёж завис в `created`: повторно запускает воркфлоу.

Остальное только фиксируется и уходит уведомлением.

## 9. Монорепо

Один `go.mod` **[предложение]**: модуль `github.com/vbloher/payment-processing-system`. Проще
многомодульного workspace; цена — общие версии зависимостей у всех сервисов.

```
api/                  контракты: OpenAPI (payment, mockbank), proto (ledger)
gen/                  сгенерированный код
pkg/                  общая инфраструктура: из шаблона + клиенты NATS и Temporal, события, тестовая инфраструктура
services/
  payment/            cmd/app, config, internal/…, migration/postgres
  ledger/             то же
  notification/       то же
  mockbank/           то же, без миграций
test/e2e/             сквозные тесты всей системы
docker-compose.yml    Postgres (три БД), NATS, Temporal с UI, четыре сервиса
Makefile, Dockerfile, .golangci.yml, .mockery.yml, .github/workflows/ci.yml
```

- `services/<name>/internal` закрывает внутренности сервиса от соседей средствами Go.
- Два отступления от шаблона, без которых четыре сервиса не запустить в одном тестовом процессе
  **[предложение]**. У каждого сервиса есть публичная точка входа `Run(ctx, config)` рядом с
  `internal`: `test/e2e` не может импортировать чужой `internal/app`. `pkg/metrics` принимает
  реестр Prometheus снаружи: в шаблоне метрики регистрируются в глобальном реестре, и второй
  сервис в том же процессе упадёт на повторной регистрации.
- `pkg/` — только инфраструктура и контракты. Доменный код между сервисами не разделяется.
- В `payment` определение саги лежит в отдельном пакете уровня use case: единственное место, где
  бизнес-логика зависит от SDK Temporal. Активности — контроллер, который вызывает use case. Клиент
  Temporal (запуск, сигнал) — адаптер за портом **[предложение]**.
- Код, комментарии и README — на английском, как в шаблоне **[предложение]**.

## 10. Тесты

**Юнит** (без Docker):

- `domain` — табличные тесты: машина состояний платежа, инвариант двойной записи, сравнение в сверке.
- `usecase` — с моками mockery, как в шаблоне.
- Воркфлоу — в тестовом окружении Temporal SDK с замоканными активностями; таблица сценариев
  покрывает каждую ветку из 6.3.

**Интеграционные** (тег `integration`, testcontainers-go, testify suite):

- На уровне сервиса: адаптеры Postgres, outbox → JetStream, inbox, gRPC леджера.
- Сквозные в `test/e2e`: Postgres, NATS и Temporal в контейнерах; четыре сервиса запускаются в
  процессе теста через публичный `Run` каждого сервиса **[предложение]**. Так быстрее и отлаживается
  проще, чем сервисы в контейнерах, и повторяет подход сьюты шаблона.

Обязательные сценарии:

| # | Сценарий | Что доказывает |
|---|---|---|
| 1 | Успешный платёж | сага; проводки сбалансированы; уведомление одно |
| 2 | Недостаточно средств | отказ без вызова банка |
| 3 | Отказ банка | компенсация: холд снят, остаток восстановлен |
| 4 | Временные ошибки банка, затем успех | ретраи; в банке ровно один перевод |
| 5 | Таймаут после обработки | неизвестный исход: `Cancel` вернул `succeeded`, платёж завершён |
| 6 | Банк недоступен до обработки, потом вернулся | `review`, холд сохранён; сверка получает `cancelled` и сигналит его: платёж `failed` |
| 7 | Банк обработал перевод и стал недоступен, потом вернулся | `review`; сверка получает `succeeded` и сигналит его: платёж `succeeded` |
| 8 | Запрос на перевод приходит после `Cancel` | банк закрыл ссылку: деньги не двигаются |
| 9 | Повтор запроса с тем же ключом; тот же ключ с другим телом | идемпотентность API |
| 10 | N параллельных платежей сверх остатка | блокировки: остаток не уходит в минус; леджер цел |
| 11 | Повторная доставка события | inbox: одно уведомление |
| 12 | Сбой публикации в NATS | outbox: событие не теряется |
| 13 | «Чужой» перевод и изменённая сумма в банке | сверка: расхождение записано один раз |
| 14 | Платёж завис в `created` | сверка перезапускает воркфлоу |

## 11. Запуск, CI, документация

- `docker compose` поднимает инфраструктуру и сервисы; `Makefile` — цели по образцу шаблона.
- CI — адаптация workflow шаблона: lint, юнит-тесты с race, проверка актуальности генерации,
  интеграционные тесты, govulncheck, сборка образов.
- README: схема, запуск, сценарий демо (curl и grpcurl), раздел «Design decisions and trade-offs» —
  ответы на вопросы, которые задаст интервьюер по каждому решению.

## 12. Объём и порядок

Четыре сервиса, порядка двухсот файлов вместе с генерацией. Порядок, при котором после каждого шага
есть работающий протестированный срез:

1. Каркас монорепо, общий `pkg`, инструменты.
2. `ledger`.
3. `mockbank`.
4. `payment`: API, БД, сага.
5. Outbox → NATS и `notification` с inbox.
6. Сверка.
7. Сквозные тесты, compose, README, CI.

## 13. Что остаётся исполнителю

- Имена пакетов и файлов, схемы таблиц и индексы, поля OpenAPI и proto.
- Конкретные значения ретраев, таймаутов, окна сверки; имена переменных окружения и порты.
- Кодировка «магических» значений mock-банка и форма admin-эндпоинтов.
- Имена subject и stream в JetStream, настройки consumer, реализация DLQ, кто создаёт stream.

  и NATS, для Temporal официального модуля нет — поднимать официальный образ `temporalio/temporal`
  (`server start-dev --ip 0.0.0.0`) обычным контейнером с зафиксированным тегом.
- Способ применения миграций в compose.
- Трассировка через Temporal (интерцептор OpenTelemetry) — желательно, но не критерий приёмки.
- Распределение сценариев из раздела 10 между интеграционным и сквозным уровнем.
